# nextjs-quant 适配层需求 v6：笔内K线不得超出端点（可配置，在 api v9 之上）

> 需求方：`D:\github\nextjs-quant`。起草：2026-10-01，基于 `cf0159c`（api v9）。
> 用户反馈：**一笔的形成过程中，会出现中间某根K线的高／低点超出这笔两个端点的情况**。用户希望这种行为可以配置。
> 以 108 课原文为准。先核实原文，结论登记进 `chan-ambiguity-decisions.md`。

## 1. 现状

`core/morphology.cpp`：

- `ValidStroke(a, b, c)` 只检查两端：`SpanEnough`（跨度）、`PriceProgress`（向上笔终点顶高于起点底分型K线高点，向下对称）、`Nested`（czsc 笔两端区间不互相包含）。分型笔只检查顶高于底。
- **不检查笔区间 (a.index, b.index) 内的原始K线**。因此可能出现：
  - 向上笔：中间某根K线的最低价 < 起点底的最低价，或最高价 > 终点顶的最高价；
  - 向下笔：中间某根K线的最高价 > 起点顶的最高价，或最低价 < 终点底的最低价。
- 产生的途径包括：同型分型因 `ValidStroke` 不达标被忽略（`StrokeStream::Add` 的 `return -1`），`RefineOne` 只在窗口内细化，包含处理吞掉的极值，以及十位 = 1（允许次高次低）本身。

## 需求方复核（2026-10-01）：百万位 1 存在死锁，暂不接入

### 现象

上证日线 2038 根（`tests/unit` 同源 SSE 样本，真实 C/V），配置 `1000000`：

- 端点只有 13 个：`10B 16T 36B 46T 51B 72T 79B 85T 105B 119T 136B 142T 157B`，**第 157 根之后的 1880 根K线没有任何新笔**；
- 把输入截到前 160 / 166 / 170 / 175 / 200 / 240 根，末端都停在 `157B`，不随新数据前进。

同一样本的默认配置 `0` 在这一段为 `136B 142T 174B 184T 190B 195T 204B 213T 227B`。

### 原因判断

- 157B（low 2644.30）之后，157→162 的上升跨度不足，不成笔；第 168、169 根K线创出更低的低点（2560.32、2536.67）。
- 按 `StrokeEnd::Extreme` 的同型延伸规则，157B 应被更极端的同型底分型替换（默认配置正是延伸到 174B）。百万位 1 的新路径没有做这一步：答复中的“候选不能连接到已定型前缀……不成笔继续等待”把**尚未成笔的末端点**也当成了不可改的前缀。
- 结果从 157B 出发的任何一笔区间都含有低于 157B 的K线，永远违反包络；157B 又永不替换，形成死锁。

因此答复中“原始包络非常严格……可能长时间不成新笔”的解释不成立：这是实现缺陷，不是口径代价。

## 答复：百万位1死锁修复（2026-10-01）

### 修复与口径

确认需求方指出的缺陷：初版AddBounded把左侧包络合法性作为末端同型延伸的前提，
157B之后的新底分型不能替换末端。初版“严格包络导致长期不成笔”的解释撤回。

修复后，已确认同型分型按默认MoreExtreme规则延伸，包含相等延伸，不再检查左侧包络门槛。
反向成笔仍须满足该笔型的跨度、价位推进/互含规则及包络，合法就新增。
同型延伸破坏尾部笔时，优先从当下已确认分型中修正起点，左右均满足ValidStroke和包络才接受；
修正不了则逐对回退被破坏的尾笔，保留新末端接续，禁止冻结等待。

影线采用“两层状态”方案：成笔包络改为包含处理后的合并K线H/L，包含端点、相等允许，
被包含处理舍弃的原始影线不阻塞成笔；尚无分型的新高/新低仅作为未确认延伸候选，
移动显示末端，fractalAt=-1，不写入真实分型表或反向成笔状态，不能独立确认买卖点。
随后真实分型确认即替换候选。未确认的最后一条画线是延伸候选，不是已确认成笔的包络保证。
